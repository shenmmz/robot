## 1. 核查明细

### 1.1 ① UiController 反向依赖 UI — ✅ 成立，但严重度被低估

**报告原话**
> 名为"logic"，实为"直接操作 mainwindow 控件的 UI 胶水"。它让 logic 层依赖 UI 层，箭头倒转。

**核查证据**（`src/logic/UiController.cpp:7-37`）
```cpp
#include "UiController.h"                       // 同层
#include "RobotController.h"                    // 同层
#include "TaskExecutor.h"                        // 同层
#include "../hardware/MotionController.h"       // 穿透 → hardware 层
#include "../models/RobotConfig.h"               // 穿透 → models 层
#include "../models/RobotState.h"                // 穿透 → models 层
#include "../../ZmotionAPI/ZmotionAPI.h"         // 穿透 → 底层 SDK 封装
#include "../../library/zauxdll2.h"              // 穿透 → 底层 DLL 头
#include "../utils/MathUtils.h"                  // 穿透 → utils 层
#include "../utils/Logger.h"                     // 穿透 → utils 层
#include "../mainwindow.h"                       // 🔴 反向依赖 UI 层
// ... + 30+ QWidget 系类
```

**核查结论**
- 反向依赖 UI 成立（报告的判断方向正确）。
- 但实际穿透面比报告描述的**广得多**：UiController 同时穿透到 hardware、models、底层 SDK 封装、底层 DLL 头、utils 五层，再反向引用 UI，是典型的"分层抽象彻底失效的胶水类"。
- 报告说"方向性错误"是**保守的准确描述**——准确说法应是"五层全穿透 + 反向引用的上帝胶水"。

**修复影响**
- 任何 UI 改动都会波及 logic（反向引用）。
- 换底层 SDK（motion 控制）时 logic 也要跟着改（穿透到底层）。
- 改 models 字段（如当前正在做的 AxisUnits 重构）也可能漏改 UiController 里的 hard-code。
- 建议**重新评估工作量**：报告说"大改造、单独排期"，实际上可能比预想更大。

> UI 层同时握着 UI、logic、hardware、底层 DLL 四层的东西——典型的"上帝窗口"反模式。

### 1.4 ④ cs_vmcontrol 死代码 — ❌ 判断错误

**报告原话**
> 视觉已彻底改 QProcess 模式（VisionController），`src/vision/cs_vmcontrol/` 整棵 VM SDK 封装树是**死代码**，却还被 UI 引用着。

**核查证据**（`mainwindow.cpp` 中的实际调用点）

| 行号 | 调用 |
|---|---|
| 172 | `m_visionLink = new VisionRobotLink(this);` |
| 924-936 | `if (!m_vmWindow) { ... } m_vmWindow->selectedProcessName();` |
| 994 | `connect(m_visionLink, &VisionRobotLink::targetReady, this, ...);` |
| 1004 | `m_vmWindow->vmControl()->executeProcedureCommand(...)` |
| 1104-1138 | VmWindow 完整生命周期：创建、ActiveX 渲染、信号连接（VMControl::dataReady / messageReady / statusChanged） |
| 3973-3979 | 视觉方案加载/执行入口 |

**核查结论**
- cs_vmcontrol **不是死代码**。B 套视觉（VmWindow + VMControl + VisionRobotLink）正在被 mainwindow 实际调用，承担"视觉定位 / 方案加载 / ActiveX 渲染"功能。
- 项目里**实际是两套并存的视觉链路**：

  | 套 | 实现 | 触发场景 |
  |---|---|---|
  | A 套（QProcess） | `src/vision/VisualRoboticArm/VisionController` | Python 视觉程序 → TCP 5001 → 姿态指令 |
  | B 套（VM SDK 内嵌） | `src/vision/cs_vmcontrol/`（VmWindow + VMControl + VisionRobotLink） | 海康 VisionMaster 方案加载 / 视觉定位 |

- mainwindow.cpp 同时持有两套：line 20 include A 套、line 15-17 include B 套的 3 个头文件。

**修正后的描述**
> cs_vmcontrol 是 B 套视觉方案的运行时实现，仍在"视觉定位"页面被实际使用。它和 A 套（VisionController / QProcess 模式）是**双轨并存**关系，不是死代码残留。

**修复建议调整**
- ❌ **不能**按"死代码"直接删 cs_vmcontrol 整棵树——会破坏视觉定位功能。
- 三条可选路径：
  1. **保留双轨**：明确 A/B 两套分别承担什么场景，文档化边界，不动代码。
  2. **统一为单套**：选定 A 或 B，把另一套真正移出（要先确认没人在用哪条场景）。
  3. **抽公共接口**：把两套视觉都封装成 `IVisionProvider`，mainwindow 只对接口编程，屏蔽差异。
- 在没有产品决策前，**不要按原报告 ④ 的建议直接清理**。
