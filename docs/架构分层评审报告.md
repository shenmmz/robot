## 1. 结论摘要

**分层骨架是健康的——models 层完全干净，vision 层已解耦。但有 4 处真实的耦合问题**，其中 1 处是"五层全穿透 + 反向引用"（logic 反向依赖 UI）、1 处是视觉双轨并存（v1.0 误判"死代码"，v1.1 修正）、2 处是越层直连。按严重度排序：

| 级别 | 问题 | 位置 | 建议 |
|------|------|------|------|
| 🔴🔴 最严重 | UiController 五层全穿透 + 反向依赖 UI | `src/logic/UiController.cpp:7-37` | 归入 UI 域，单独排期（工作量上调） |
| 🔴 | mainwindow 上帝窗口 | `mainwindow.cpp` 多处 | 收口到 logic/hardware，大改造 |
| 🔴 | logic 绕过 hardware 直连 ZmotionAPI | 5 处：`TaskExecutor.cpp:12` / `RobotController.cpp:17` / `RobotController.h:48` / `HomingController.cpp:4` / `UiController.cpp:13` | 收口 ZmotionAPI，中等 |
| 🟡 | cs_vmcontrol 双轨并存（B 套视觉在用，**不可删**） | `mainwindow.cpp:15-17` + 6 处实际调用点 | 需产品决策：保留双轨 / 统一单套 / 抽接口 |
| 🟡 | include 风格不统一等 | 全局 | 顺手可改 |

建议执行顺序：**P0 修正事实判断（本版已完成）→ P1 视觉链路产品决策 → ③ → ②①**。

## 4. ✅ 干净的部分（先肯定）

### 4.1 models 层零外部依赖 —— 最干净的一层
`RobotConfig` / `RobotKinematics` / `RobotState` / `RobotModels` 只依赖 Qt 和自己层内，**不 include 任何上层头文件**。当前正在做的 `getAxisUnitsList()` 实时推导重构正好落在这层，安全且无冲突。

### 4.2 vision 层已解耦
`VisualRoboticArm/VisionController.cpp` 走 QProcess 方案，include 里全是 Qt（QTcpServer / QProcess / QJson），**不再碰 VM SDK**。"QProcess 取代内嵌 SDK"的决策在代码上成立。

### 4.3 utils / hardware 内部
无越界。

## 5. 🔴 耦合问题（按严重度排序）

### 5.1 ① UiController 放在 logic 层，五层全穿透 + 反向依赖 UI（最严重，🔴🔴）

**证据**（`src/logic/UiController.cpp:7-37`，v1.1 补全穿透面）
```cpp
#include "UiController.h"                       // 同层
#include "RobotController.h"                    // 同层
#include "TaskExecutor.h"                       // 同层
#include "../hardware/MotionController.h"       // 🔴 穿透 → hardware 层
#include "../models/RobotConfig.h"              // 🔴 穿透 → models 层
#include "../models/RobotState.h"               // 🔴 穿透 → models 层
#include "../../ZmotionAPI/ZmotionAPI.h"        // 🔴 穿透 → 底层 SDK 封装
#include "../../library/zauxdll2.h"             // 🔴 穿透 → 底层 DLL 头
#include "../utils/MathUtils.h"                 // 🔴 穿透 → utils 层
#include "../utils/Logger.h"                    // 🔴 穿透 → utils 层
#include "../mainwindow.h"                      // 🔴🔴 反向依赖 UI 层
// ... + 30 余个 QWidget 系类（QComboBox / QDoubleSpinBox / ...）
```

**问题**
名为"logic"，实为"直接操作 mainwindow 控件的 UI 胶水"。它同时穿透 hardware、models、底层 SDK、底层 DLL 头、utils **五层**，再反向 include `../mainwindow.h`——是"分层抽象彻底失效的上帝胶水"，比 v1.0 所说的单纯"方向性错误"严重得多：
- 任何 UI 改动都会波及 logic（反向引用）
- 换底层运动 SDK 时 logic 也要跟着改（穿透到底层）
- 改 models 字段（如 AxisUnits 重构）也可能漏改 UiController 里的硬编码

**建议**
- 它要么归入 `src/ui/`（它本质是 UI 控制器），要么拆出纯业务部分、把控件操作留在 UI。
- **工作量比 v1.0 预估更大：五层穿透全部要拆，必须单独排期，不建议混在本次重构里。**

### 5.2 ② mainwindow（UI 层）越两级直连底层 DLL —— 上帝窗口反模式

**证据**（`mainwindow.cpp`）
- `:22` `#include "library/zmotion.h"`
- `:25` `#include "library/zauxdll2.h"`
- `:37` `#include "ZmotionAPI/ZmotionAPI.h"`
- `:18-19` 直接 include hardware 的 `Rs485Controller` / `ServoController`

**问题**
UI 层应该只跟 logic 层对话。现在 mainwindow 同时握着 UI、logic、hardware、底层 DLL 四层的东西——`Robot_R06` 里 `RobotController.cpp`（约 700 行）之外的硬件调用散在 UI 里，这是典型的"上帝窗口"反模式。

**建议**
凡是 mainwindow 直接调 ZmotionAPI 的地方，收口到 RobotController 或新建的硬件服务里。**属于大改造**，短期可先列清单，逐项迁移。

### 5.3 ③ TaskExecutor（logic 层）绕过 hardware 直连 ZmotionAPI

**证据**（共 **5 处**：4 个 .cpp + 1 个 .h，v1.1 补全）
- `src/logic/TaskExecutor.cpp:12`：`#include "../../ZmotionAPI/ZmotionAPI.h"`
- `src/logic/RobotController.cpp:17`：同上
- `src/logic/RobotController.h:48`：**头文件层**也直接 include（v1.1 补，核查意见亦未列）
- `src/logic/HomingController.cpp:4`：同上
- `src/logic/UiController.cpp:13`：同上（核查意见补列）

**问题**
logic 直接调底层，等于 **hardware 抽象层形同虚设**——换个控制器 SDK 时 logic 层也要跟着改。

**建议**
中长期让 `ZmotionAPI` 只被 hardware 层 include，logic 一律经 RobotController / MotionController 间接调用。这比 ①② 小，可以列入待办。

### 5.4 ④ cs_vmcontrol 与 VisionController 双轨并存（🟡，v1.1 修正：v1.0 "死代码"判断有误）

**证据**（`mainwindow.cpp` 实际调用点，非仅 include）
- `:15-17` include 三个 cs_vmcontrol 头文件（`VisionRobotLink.h` / `vmcontrol.h` / `VmWindow.h`）
- `:172` `m_visionLink = new VisionRobotLink(this);`
- `:994` `connect(m_visionLink, &VisionRobotLink::targetReady, ...)`
- `:1004` `m_vmWindow->vmControl()->executeProcedureCommand(...)`（拿水流程逐帧拍摄）
- `:1100-1141` **视觉定位按钮 onBtnVerifyVision() 就是 B 套入口**：`new VmWindow()` + ActiveX 渲染 + VMControl 三信号连接（dataReady / messageReady / statusChanged）
- `:3971-3980` `initVisionAutoLoad()` 启动时也创建 VmWindow
- 同时 A 套也在运行：`:163-169` `new VisionController` + 6 个信号连接

**问题**
项目里实际是**两套并存的视觉链路**，不是死代码：

| 套 | 实现 | 触发场景 |
|---|---|---|
| A 套（QProcess） | `src/vision/VisualRoboticArm/VisionController` | 独立视觉程序 → TCP → 姿态指令 |
| B 套（VM SDK 内嵌） | `src/vision/cs_vmcontrol/`（VmWindow + VMControl + VisionRobotLink） | 视觉定位 / 方案加载 / ActiveX 渲染 / 拿水流程拍摄 |

**❌ 不能按"死代码"直接删**——删掉会立即破坏视觉定位页功能（编译失败 + 运行时该页面所有交互崩溃）。

**建议**（需产品决策，决策前不动代码）
1. **保留双轨**：明确 A/B 各自承担的场景，文档化边界
2. **统一为单套**：选定 A 或 B，把另一套真正移出（先确认没有使用方）
3. **抽公共接口**：两套都封装成 `IVisionProvider`，mainwindow 只对接口编程，屏蔽差异

> **方法论教训（v1.1）**：v1.0 在此处未做完 grep 实际符号引用就下了"死代码"结论。今后任何"可删/死代码"判断，必须先 grep 完整调用链（include + 实际符号使用）。
