## 2026-08-27（第九次修改）

### 问题描述
程序运行时报错：`This application failed to start because no Qt platform plugin could be initialized.`
控制台输出：`qt.qpa.plugin: Could not find the Qt platform plugin "windows" in ""`

### 根本原因
`CMakeLists.txt` 中原有的 Qt 部署代码（手动从 Qt 安装目录逐个拷贝 DLL 和插件目录）未生效。虽然路径推导逻辑正确、源文件存在，但 POST_BUILD 命令没有实际执行，导致构建输出目录中缺少 `platforms/qwindows.dll` 和 Qt6 核心 DLL。同时 `qt.conf` 虽然在 CMake 配置阶段生成，但缺少配套的插件文件，Qt 仍找不到平台插件。

### 修改内容
**文件**: `CMakeLists.txt`（第 207-232 行）

将原有手动拷贝 Qt DLL 和插件目录的 POST_BUILD 命令替换为 Qt 官方 `windeployqt` 工具：

1. **删除的代码**：手动遍历拷贝 `Qt6Core.dll`/`Qt6Gui.dll` 等 DLL、逐个拷贝 `platforms`/`styles`/`imageformats` 等插件目录、手动生成 `qt.conf` 的三段代码（约 50 行）

### 修改原理
`windeployqt` 是 Qt 官方部署工具，能自动分析 exe 的依赖关系并拷贝所有需要的 DLL 和插件。相比手动逐个指定文件名的方式更可靠，不会遗漏依赖，且 Qt 版本升级后无需手动更新文件列表。

## 2026-07-20（第七次修改 - 最终版）

### 问题描述
"功能测试"按钮点击后，Python 进程启动但视觉窗口没有显示。先后出现两种错误：
1. `No Python at 'MarvisAgent/python.exe'` — pyvenv.cfg 指向已不存在的 MarvisAgent Python
2. `Failed to import encodings module` — 设置 PYTHONHOME 指向 venv 目录后，Python 找不到标准库

### 根本原因
- **问题1**：虚拟环境 `.venv` 是用腾讯 MarvisAgent 的 Python 创建的，`pyvenv.cfg` 中的 `home` 指向 MarvisAgent 路径，该路径已不存在
- **问题2**：为解决问题1，手动设置了 `PYTHONHOME` 指向 venv 目录，但 venv 目录中**没有标准库**（标准库在基础 Python 安装中），导致 Python 无法加载 `encodings` 模块

### 解决方案
1. **重新创建虚拟环境**：用系统上可用的 Python（miniconda3 Python 3.13）重新创建 venv，并安装依赖
2. **正确处理环境变量**：删除 `PYTHONHOME` 和 `PYTHONPATH`（不设置新值），让 venv 的 `python.exe` 通过 `pyvenv.cfg` 自行解析路径

### 修改内容
**文件**: `src/vision/VisualRoboticArm/VisionController.cpp`

```cpp
// 清理可能干扰虚拟环境的环境变量：
// - PYTHONHOME/PYTHONPATH 会导致 Python 忽略 venv 的 pyvenv.cfg，指向错误路径
// - QT_PLUGIN_PATH 可能导致 PySide6 加载错误的 Qt 插件
env.remove(QStringLiteral("PYTHONHOME"));
env.remove(QStringLiteral("PYTHONPATH"));
env.remove(QStringLiteral("QT_PLUGIN_PATH"));
```

### venv 工作原理（小白版）
- venv 的 `python.exe` 启动时会读取同目录的 `pyvenv.cfg`
- `pyvenv.cfg` 中的 `home` 字段告诉 Python 去哪里找标准库
- 设置 `PYTHONHOME` 会**覆盖**这个机制，导致 Python 去错误的路径找标准库
- 所以对于 venv：**不要设置 PYTHONHOME**，只删除系统中可能存在的错误 PYTHONHOME 即可

### 验证方法
重新编译运行程序，点击"功能测试"按钮，应不再出现 `No Python at` 错误，视觉窗口应该正常显示。

## 2026-07-20（第四次修改）

### 问题描述
程序运行时出现大量重复的错误日志：
```
QTcpServer::listen() called when already listening
[MainWindow] 视觉程序错误: "Vision TCP Server 启动失败: "
```

### 根本原因
`VisionController::start()` 函数中，`isRunning()` 只检查 Python 进程是否在运行，没有检查 `QTcpServer` 是否已经在监听。

当发生以下情况时：
1. 第一次调用 `start()`，TCP Server 创建并开始监听
2. Python 进程启动失败（或其他原因）
3. 再次调用 `start()`，由于 `isRunning()` 返回 false
4. 尝试再次调用 `listen()`，但 server 已经在监听，导致错误

### 修改内容
**文件**: `src/vision/VisualRoboticArm/VisionController.cpp`

**位置**: `start()` 函数，第81-87行

**修改前**:
```cpp
if (!m_tcpServer) {
    m_tcpServer = new QTcpServer(this);
    connect(m_tcpServer, &QTcpServer::newConnection,
            this, &VisionController::onNewConnection);
}
if (!m_tcpServer->listen(QHostAddress::LocalHost, kServerPort)) {
    emit errorOccurred(QStringLiteral("Vision TCP Server 启动失败: %1")
                       .arg(m_tcpServer->errorString()));
    return false;
}
```

**修改后**:
```cpp
if (!m_tcpServer) {
    m_tcpServer = new QTcpServer(this);
    connect(m_tcpServer, &QTcpServer::newConnection,
            this, &VisionController::onNewConnection);
}
// 如果 server 已经在监听，跳过 listen() 调用
if (!m_tcpServer->isListening()) {
    if (!m_tcpServer->listen(QHostAddress::LocalHost, kServerPort)) {
        emit errorOccurred(QStringLiteral("Vision TCP Server 启动失败: %1")
                           .arg(m_tcpServer->errorString()));
        return false;
    }
}
```

### 修改原理
在调用 `listen()` 之前，先使用 `QTcpServer::isListening()` 检查 server 是否已经在监听状态。如果已经在监听，就跳过 `listen()` 调用，避免重复监听导致的错误。

### 验证方法
重新编译运行程序，观察是否还有 "QTcpServer::listen() called when already listening" 错误。

   ```
   C:\Program Files\VisionMaster4.4.0\Development\V4.x\Includes\MVD_AlgoParamDefine.h:150: warning: C4091: "typedef ": 没有声明变量时忽略"VisionDesigner::_MVD_CALIPERTOOL_EDGEMODE__"的左侧
   ```

### 根本原因
1. **LNK2005 错误**：`VisionMasterAdapter.h` 被放在了 `target_sources(vm_control PUBLIC ...)` 中。由于这个头文件包含 `Q_OBJECT` 宏，Qt 的 AUTOMOC 会扫描所有源文件（包括 PUBLIC 传递的头文件）并生成 moc 代码。这样 `vm_control` 库和依赖它的目标（`robot_vision` 以及最终可执行文件）都会生成一份 `VisionMasterAdapter` 的 moc 代码，链接时就会出现多重定义错误。
2. **C4091 警告**：VisionMaster SDK 头文件中的 typedef 写法不规范，触发了 MSVC 的 C4091 警告。

### 修改内容
**文件**: `src/vision/CMakeLists.txt`

**修改1**：将 `cs_vmcontrol` 目录通过 `target_include_directories(vm_control PUBLIC ...)` 公开给外部目标，删除 `target_sources(vm_control PUBLIC ...)` 中对头文件的声明：

**修改前**:
```cmake
target_include_directories(vm_control PRIVATE
    ${CMAKE_CURRENT_SOURCE_DIR}/cs_vmcontrol
    ${VM_INCLUDE_DIRS}
    ${VM_QT_INCLUDE_DIRS}
)
...
target_sources(vm_control PUBLIC
    cs_vmcontrol/VisionMasterAdapter.h
)
```

**修改后**:
```cmake
target_include_directories(vm_control PUBLIC
    ${CMAKE_CURRENT_SOURCE_DIR}/cs_vmcontrol
)

target_include_directories(vm_control PRIVATE
    ${VM_INCLUDE_DIRS}
    ${VM_QT_INCLUDE_DIRS}
)
```

**修改2**：添加 `/wd4091` 编译选项禁用 C4091 警告：

**修改前**:
```cmake
if(MSVC)
    target_compile_options(vm_control PRIVATE 
        /source-charset:gbk 
        /execution-charset:utf-8 
        /wd4828
        /wd4819
    )
endif()
```

**修改后**:
```cmake
if(MSVC)
    target_compile_options(vm_control PRIVATE 
        /source-charset:gbk 
        /execution-charset:utf-8 
        /wd4828
        /wd4819
        /wd4091
    )
endif()
```

### 修改原理
1. **正确公开头文件**：在 CMake 中，头文件应该通过 `target_include_directories` 来公开包含目录，而不是通过 `target_sources` 把 `.h` 文件当作源文件传递。`target_sources(PUBLIC ...)` 会把头文件当作源文件传递给依赖目标，导致 AUTOMOC 重复扫描并生成重复的 moc 代码。
2. **禁用 C4091 警告**：VisionMaster SDK 是第三方库，我们不能修改它的头文件，所以用 `/wd4091` 禁用这个不影响编译正确性的警告。

## 2026-07-01

### 问题描述
执行 `script.rbt` 脚本时，每个 `MOVEL` 指令都报 "等待运动到位超时"。

### 根本原因
在 **CONNFRAME 模式**（逆解模式）下：
- 虚拟轴 (6-11) 接收运动指令，是主动轴
- 关节轴 (0-5) 由虚拟轴通过 DH 模型自动解算并联动驱动，是从动轴

原代码使用 `waitForAxesIdle(jointAxes)` 等待关节轴停止，但 `GetIfIdle` API 对从动轴的状态检测不准确，导致即使关节轴已到达目标位置，仍可能返回 "运动中" 状态，从而引发超时。

### 修改内容
**文件**: `src/logic/RobotController.cpp`

**位置**: `moveL` 函数（约第595-599行）

**修改前**:
```cpp
// 等待关节轴运动停止(CONNFRAME 模式下虚拟轴会先到位,关节轴后到位)
QList<int> jointAxes = m_config->getJointAxisList();
result = api->waitForAxesIdle(jointAxes, timeoutMs);
```

**修改后**:
```cpp
// 等待虚拟轴到达目标位置(CONNFRAME 模式下虚拟轴直接执行运动指令)
// 注意：不能使用关节轴的waitForAxesIdle，因为在CONNFRAME模式下关节轴是
// 由虚拟轴通过DH模型联动驱动的从动轴，GetIfIdle对从动轴的状态检测不准确
result = api->waitForAxesReachTarget(virtualAxes, dposTargets, timeoutMs, 0.5f);
```

### 修改原理
- `waitForAxesReachTarget` 通过轮询 `GetDpos`（实际位置）并与目标位置对比来判断运动是否完成
- 这种方式直接读取位置值，不依赖 IDLE 状态，更适合 CONNFRAME 联动模式
- 容差设置为 0.5mm，对于笛卡尔空间运动是合理的阈值

### 验证方法
重新编译运行程序，执行 `script.rbt` 脚本，观察是否还有 "等待运动到位超时" 的警告。
